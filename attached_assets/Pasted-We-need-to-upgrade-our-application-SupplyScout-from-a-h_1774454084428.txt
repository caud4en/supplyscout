We need to upgrade our application (SupplyScout) from a hackathon prototype into a production-ready product.

Right now, the system demonstrates the concept well, but there are several critical gaps that must be fixed to ensure the application is real, reliable, and usable in the real world.

🚨 Core Issues Identified

Supplier Website URLs Are Not Verified

Current URLs are generated based on company names

Many links are invalid or do not point to real official websites

This breaks trust and usability

RFQ Workflow Is Not Functional

“Send RFQ” button does nothing

No actual output or usable result is generated

Incomplete / Demo-Only Features Are Visible

Features that are not fully working are still shown in the UI

This makes the product feel unfinished and unreliable

🎯 What We Need (High Priority Fixes)
1.⁠ ⁠Verified Real Supplier Websites

We need to ensure that:

Every supplier in the database has a real, valid, official website URL

URLs must NOT be guessed or generated from company names

They must be:

scraped from real directories

validated as working links

pointing to the actual company website (not placeholder pages)

If a supplier does NOT have a verified website:

Do NOT display a fake or guessed URL

Either:

leave it blank, or

exclude that supplier from results

The goal is:

Every link shown in the UI must be real and clickable.

2.⁠ ⁠Improve Data Quality (Real-World Readiness)

The supplier database must contain:

real company names

real locations

real capabilities

real certifications (if available)

real descriptions

If current data is partially synthetic or inferred, it must be:

replaced with real scraped data, OR

clearly filtered so only reliable entries are shown

3.⁠ ⁠RFQ Workflow Redesign (No Fake Sending)

We do NOT need to send RFQs to suppliers yet.

Instead:

When user clicks “Send RFQ”, the system should:

generate a proper RFQ draft document

include:

supplier name

product specification

quantity

requirements

allow user to:

download it (PDF or text)

copy it

This makes the feature:

useful

realistic

safe (no unintended emails)

4.⁠ ⁠Remove or Hide Non-Functional Features

Any feature that is not fully working must:

be removed from the UI, OR

be disabled and clearly marked

Examples:

broken RFQ buttons → replace with “Generate RFQ Draft”

incomplete TinyFish live browsing → hide if unreliable

The product must feel:

clean, intentional, and production-ready — not a demo with broken parts.

5.⁠ ⁠Ensure System Consistency

The system should behave as a real SaaS product, not a prototype:

all displayed data must be real and trustworthy

all buttons must perform meaningful actions

no dead links

no fake outputs

no placeholder functionality
